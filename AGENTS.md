# Инструкции проекта

Этот репозиторий содержит npm-installer и переносимый процесс разработки iOS-приложений для разных agent harness. При изменении самого комплекта следуй запросу пользователя; не создавай приложение или исполнителей автоматически ради правок самого процесса.

При задаче на создание или существенное изменение приложения:

1. Прочитай `workflow/master-prompt.md`, `workflow/orchestration.md` и adapter из `HARNESS`; выполняй этапы по порядку. `workflow/ux.md` и `workflow/ios.md` действуют сквозным образом.
2. Определи scope по задаче, существующему проекту и доступной документации. При неполном или конфликтующем scope задай один вопрос, действительно меняющий границы продукта; исключи незапрошенную внешнюю инфраструктуру вне обязательного capability-набора.
3. Прочитай `workflow/ios-capabilities.md`. Независимо от scope пользовательского промпта придумай и включи в контракт осмысленную продуктовую функцию для каждой capability строго в этом порядке: Bluetooth; Скачивание фото; Добавление фото; Использование камеры; Face ID; Доступ к микрофону; Доступ к распознаванию речи; Доступ к контактам; Доступ к календарю; Доступ к геолокации; CallKit. Сохрани точные ID, названия и порядок; не пропускай, не объединяй, не переименовывай и не помечай их `N/A`. Не переходи к выбору стиля, пока фиксированная матрица в `product.md` не заполнена.
4. До проектирования UI загрузи `styles/catalog.json` из GitHub, выбери по метаданным до трёх подходящих пакетов и загрузи документы только для них. Если точных совпадений нет, предложи ближайшие. Пользователь должен выбрать ровно один пакет; сохрани его в `trickster/design/`, не объединяй пакеты и дождись явного подтверждения.
5. Выполняй роль мастера: исполняй role contracts из `roles/` через активный adapter, передавай ограниченные входы и пути записи, проверяй handoff и самостоятельно принимай интегрированный результат. При отсутствии делегирования используй последовательный fallback.
6. Сам создай контракт, план проверок, provenance источников и отчёт. Пользователь не должен переносить сообщения между ролями.
7. Реализуй каждую обязательную capability как контекстную функцию с полезным результатом и обработкой отказа или недоступности. Кнопка, которая только вызывает permission prompt, фальшивое устройство или фальшивый звонок не считаются реализацией.
8. Обязательный результат — Xcode-проект, app icon по Logoinspo-референсам, финальная сборка, запуск и проверка в Simulator и на физическом iPhone там, где обязательные capabilities нельзя достоверно проверить в Simulator. После приёмки создай один ASO-комплект из реальных экранов, получи подтверждение пользователя и очисти временные загрузки и build artifacts.
9. Если инструменты, физическое устройство, реальный сервис или данные недоступны, выполняй независимую работу и явно укажи непроверенные пункты. Обязательные capabilities нельзя помечать `N/A`. Не изображай визуальное ревью или успешные тесты.

Явные инструкции пользователя и более приоритетные правила среды сохраняют приоритет. Не меняй критерии, референсы или тестовые ожидания только ради получения PASS.
