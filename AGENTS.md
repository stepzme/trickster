# Инструкции проекта

Этот репозиторий содержит npm-installer и переносимый процесс разработки iOS-приложений для разных agent harness. При изменении самого комплекта следуй запросу пользователя; не создавай приложение или исполнителей автоматически ради правок процесса.

При создании или существенном изменении приложения:

1. Прочитай `workflow/master-prompt.md`, `workflow/orchestration.md` и adapter из `HARNESS`. Выполняй пять стадий: Research, Planning, Design, Dev, Publish.
2. Research описывает весь продукт без деления на MVP и Full Scope. Product Researcher включает все одиннадцать capabilities в фиксированном порядке и получает явное подтверждение пользователя.
3. После Research Planning и исследование референсов могут идти параллельно. Planning делит утверждённый продукт на дизайн-MVP и крупные блоки Full Scope и получает явное подтверждение пользователя.
4. Designer выбирает до трёх приложений из каталога, предлагает один UI reference, один UX reference и опциональный illustrations reference и получает явное подтверждение пользователя. UX определяет только навигацию, взаимодействия и переходы, но не визуальные свойства.
5. Не синтезируй новый обобщённый проектный `ui.md`, `composition.md` или provenance-документ. Копируй утверждённые исходные `ui.md`, `ux.md` и опциональный `illustrations.md` без переписывания.
6. После утверждения Planning тот же Designer сам реализует MVP в Xcode, включая необходимую графику, и показывает реально запущенное приложение в Simulator. Только явное подтверждение этой сборки считается утверждением дизайна. Текст, evidence frames и успешная сборка его не заменяют.
7. После утверждения дизайна Implementation Owner развивает эту же сборку до Full Scope крупными блоками. Каждый блок отдельно показывается пользователю и требует явного подтверждения до начала следующего.
8. Designer владеет иллюстрациями, изображениями, app icon и store screenshots. Store screenshots создаются только после появления подходящих реальных экранов.
9. Acceptance Reviewer на стадии Publish проверяет все подтверждения, финальную сборку, соответствие референсам, продуктовые сценарии и capabilities. Он не исправляет код. После финального подтверждения пользователя он удаляет только записанные временные файлы и build artifacts.
10. Product Researcher следует единому capability-контракту в `roles/product-researcher.md`. Все downstream-роли следуют capability-решениям из утверждённого Research.
11. Не добавляй собственный backend, серверные аккаунты, Sign in with Apple, CloudKit или синхронизацию без прямого требования пользователя. Храни необходимые локальные данные простейшим подходящим способом.
12. Недоступные проверки описывай простыми словами. Не изображай системный prompt, визуальное ревью или успешный тест.

Явные инструкции пользователя и более приоритетные правила среды сохраняют приоритет. Не меняй критерии, референсы или ожидания только ради положительного результата.

## Тесты комплекта

Пиши тесты только для исполняемого поведения и устойчивых инвариантов: installer, package contents, canonical capability data, catalog integrity и сохранность пользовательских artifacts. Смысловую согласованность инструкций проверяй ревью документов, а не regex-тестами отдельных фраз.

## Git

Репозиторий проекта: https://github.com/stepzme/trickster.
После завершения задачи фиксируй изменения проекта коммитом и отправляй их в GitHub, если пользователь не указал иное. Не добавляй секреты и локальные артефакты сборки. При ошибке push явно сообщи, что осталось только локально.
