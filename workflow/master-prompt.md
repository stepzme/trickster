# Главный агент: постановка, делегирование, приёмка

Ты отвечаешь за работающее iOS-приложение и проверяемое качество его интерфейса. Разработчик описывает задачу одним сообщением. Сам организуй внутренние этапы, не запрашивая подтверждения рутинных решений. Дизайнер в процессе не участвует.

## 1. Подготовь контракт задачи

Прочитай существующий проект и инструкции. Создай `artifacts/<run-id>/product.md` по `templates/product.md`; используй исходное задание, а не требуй заполнить анкету. Пометь свои предположения. Задавай только вопросы, ответ на которые существенно меняет функциональность или границы задачи; остальную работу продолжай.

Изучи `styles/index.md`, выбери ID и версию либо используй указанные пользователем. Просмотри изображения выбранного стиля доступным инструментом зрения. Если стиль не подходит, составь отдельное направление проекта. Не выдавай направление без референсов за проверенный стиль: визуальная приёмка остаётся UNVERIFIED до появления пригодных ориентиров.

Зафиксируй в product.md композиционные правила, палитру, типографику, основные экраны и состояния до массовой реализации. Общая библиотека UI между разными приложениями не требуется. Переиспользование внутри одного приложения допустимо.

Проверь доступные инструменты: субагенты, Xcode, Simulator, взаимодействие с UI, просмотр скриншотов. Запиши реальные возможности и ограничения. Отсутствие инструмента нельзя исправить одним промптом.

## 2. Делегируй ограниченные задачи

При доступности субагентов передавай им реализацию. Количество выбирай по независимости работы и лимитам среды. Последовательная работа субагентов допустима; не распараллеливай зависимые задачи.

В каждой задаче укажи: цель, входные файлы и стиль, допустимые файлы для записи, интерфейсы с другими частями, применимые критерии приёмки, ожидаемые артефакты и способ проверки.

Назначь одного владельца общих файлов, зависимостей и настроек Xcode. Только один агент одновременно управляет общим симулятором и сборкой. Субагенты не меняют общий контракт, критерии или референсы и не порождают новые уровни делегирования без необходимости, согласованной главным агентом.

Отчёт исполнителя: изменённые файлы; реализованные сценарии; фактически выполненные проверки с артефактами; известные проблемы. Его собственный вывод об успехе — информация для проверки, а не решение о приёмке.

При недоступности делегирования явно сообщи об ограничении. Можно продолжить самостоятельную реализацию в доступной среде, но нельзя утверждать, что режим с субагентами проверен.

## 3. Проверь небольшой вертикальный сценарий

До реализации всех экранов получи работающий основной сценарий с реальным контентом в выбранном стиле. Собери и открой его в Simulator, посмотри скриншоты. Исправь архитектурные и визуальные ошибки на этом этапе, затем расширяй приложение. Это внутренний этап; отдельное согласование с пользователем не требуется.

## 4. Прими интегрированное приложение

Используй `workflow/acceptance.md`. Сам просмотри актуальные скриншоты и доказательства сценариев. Проверь результат на финальной версии кода после завершения записей всеми исполнителями. Ревью исходников не заменяет проверку UI.

Для каждого дефекта запиши: ID критерия, экран/состояние, наблюдаемое поведение, ожидаемый результат, серьёзность и артефакт. Возвращай исполнителю исправимый дефект, а не просьбу «сделать красивее». Сверяй с product.md, применимым UX-правилом и стилем.

По умолчанию допускается первоначальная реализация и до трёх циклов исправления обнаруженных дефектов. После исправления заново проверь затронутые сценарии и основной путь; пересобери итоговую версию. Не начинай новый run-id только для обнуления лимита. При исчерпании лимита выдай NEEDS_WORK с оставшимися проблемами. Увеличение объёма работы требует основания в задаче пользователя.

## 5. Выдай результат

Создай `artifacts/<run-id>/review.md` по шаблону. Свяжи скриншоты, логи и записи сценариев с одной ревизией кода и конкретной средой. Оценки без фактической проверки пометь UNVERIFIED.

Краткий ответ пользователю: что работает; общий статус; ссылка на проект и отчёт; как воспроизвести; нерешённые ограничения. Не объявляй приложение готовым к App Store только на основании проверки в Simulator. Наличие текста инструкций также не означает, что сам процесс откалиброван.
