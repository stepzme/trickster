# Инструкции проекта

Этот репозиторий содержит npm-installer и переносимый процесс разработки iOS-приложений для разных agent harness. При изменении самого комплекта следуй запросу пользователя; не создавай приложение или исполнителей автоматически ради правок самого процесса.

При задаче на создание или существенное изменение приложения:

1. Прочитай `workflow/master-prompt.md`, `workflow/orchestration.md` и adapter из `HARNESS`; выполняй этапы по порядку. `workflow/ux.md` и `workflow/ios.md` действуют сквозным образом.
2. Выполни единый этап product definition: определи core scope по задаче, существующему проекту и документации, затем синтезируй все обязательные capabilities и только после этого зафиксируй final reconciled scope. При неполном или конфликтующем итоговом scope задай один вопрос, действительно меняющий границы продукта; исключи незапрошенную внешнюю инфраструктуру вне обязательного capability-набора.
3. Прочитай `workflow/ios-capabilities.md`. Независимо от пользовательского промпта придумай и включи в контракт осмысленную продуктовую функцию для каждой capability строго в этом порядке: Bluetooth; Скачивание фото; Добавление фото; Использование камеры; Face ID; Доступ к микрофону; Доступ к распознаванию речи; Доступ к контактам; Доступ к календарю; Доступ к геолокации; CallKit. Сохрани точные ID, названия и порядок; не пропускай, не объединяй, не переименовывай и не помечай их `N/A`.
4. До проектирования UI загрузи `styles/catalog.json` из GitHub, выбери по метаданным до трёх подходящих приложений и загрузи документы только для них. Пользователь может выбрать один reference для `ui`, один для `ux` и необязательный reference для `illustrations`; один и тот же reference может выполнять несколько ролей. Не смешивай приложения по отдельным экранам или компонентам. Синтезируй один согласованный пакет в `trickster/design/` и дождись явного `DESIGN COMPOSITION APPROVED`.
5. Выполняй роль мастера: исполняй role contracts из `roles/` через активный adapter, передавай ограниченные входы и пути записи, проверяй handoff и самостоятельно принимай интегрированный результат. При отсутствии делегирования используй последовательный fallback.
6. Сам создай контракт, план проверок, provenance источников и отчёт. Пользователь не должен переносить сообщения между ролями.
7. Раздели реализацию на Core, Full и Hardening. Сначала реализуй основные разделы и primary flow, собери и покажи их пользователю и повторяй feedback loop до `CORE UI APPROVED`. Затем реализуй остальной scope и все capabilities. После Full создай и внедри утверждённые product assets и применимую app icon; только затем выполни Hardening финального интерфейса, включая ошибки, отказы, недоступность, accessibility, compact layout, локали и регрессии ассетов. По просьбе пользователя на каждой из трёх стадий собери и запусти текущую ревизию в Simulator и покажи результат как `PREVIEW`, а не как acceptance.
8. Реализуй каждую обязательную capability как контекстную функцию с полезным результатом и обработкой отказа или недоступности. Кнопка, которая только вызывает permission prompt, фальшивое устройство или фальшивый звонок не считаются реализацией.
9. После утверждения design composition параллельно с реализацией запусти app-icon branch. Используй последнюю доступную в среде модель генерации изображений, запиши точный model ID и provenance, покажи изображение пользователю и продолжай ту же концепцию до `APP ICON APPROVED`. До подтверждения не внедряй изображение в Xcode-проект.
10. План product assets входит в контракт, но их генерация и интеграция начинаются только после Full. Hardening выполняется уже с утверждённой app icon и всеми утверждёнными assets.
11. После независимой приёмки создай store screenshots только из реальных экранов принятой сборки. Сначала согласуй storyboard, затем генерируй и показывай каждый кадр отдельно; не переходи к следующему до `STORE FRAME <n> APPROVED`. После подтверждения всего набора получи финальное подтверждение пользователя и очисти временные загрузки и build artifacts.
12. Если инструменты, физическое устройство, реальный сервис или данные недоступны, выполняй независимую работу и явно укажи непроверенные пункты. Обязательные capabilities нельзя помечать `N/A`. Не изображай визуальное ревью или успешные тесты.

Явные инструкции пользователя и более приоритетные правила среды сохраняют приоритет. Не меняй критерии, референсы или тестовые ожидания только ради получения PASS.

## Тесты комплекта

Пиши тесты только для исполняемого поведения и устойчивых инвариантов: installer, package contents, schemas, canonical capability data, catalog integrity и сохранность пользовательских artifacts. Не добавляй regex-тесты ради проверки наличия отдельных формулировок в инструкциях; смысловую согласованность prose проверяй ревью документов или структурным валидатором, если появляется реальная машиночитаемая схема.
