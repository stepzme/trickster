# Trickster: iOS app development process

When creating or substantially changing an app:

1. Read `trickster/workflow/master-prompt.md`, `trickster/workflow/orchestration.md`, `trickster/adapters/contract.md`, and the adapter named in `trickster/HARNESS`; execute every applicable stage in order. `ux.md`, `ios.md`, and `launch-screen.md` apply across all stages.
2. Perform one product-definition stage. Derive the core scope from the request, existing project, and documentation; synthesize all mandatory capabilities; then reconcile the final scope. Every Trickster project is local-first: store durable product data in SwiftData, binary data in files, create identity locally without registration, and reserve `UserDefaults` for small preferences. Do not add a proprietary backend, server accounts, Sign in with Apple, CloudKit, or synchronization. If the product cannot be delivered honestly within this boundary, mark the scope `CONFLICTING` and ask one question that changes the product boundary.
3. Read `trickster/workflow/ios-capabilities.md`. Regardless of the user's prompt, invent and contract one coherent product feature for every capability in this exact order: Bluetooth; Downloading Photos; Adding Photos; Using the Camera; Face ID; Microphone Access; Speech Recognition Access; Contacts Access; Calendar Access; Location Access; CallKit. Preserve their exact IDs, names, and order; do not omit, merge, rename, replace, or mark a row `N/A`. CallKit alone may be contracted as `INTERFACE_ONLY` without signaling or media transport; every other capability requires a real useful result.
4. Before UI implementation, load the GitHub catalog, shortlist no more than three suitable apps by metadata, and load documents only for those apps. The user may assign one reference to UI, one to UX, and an optional one to illustrations; the same app may serve more than one concern. Do not mix references per screen or component.
5. Synthesize one coherent local design package in `trickster/design/`, record provenance and conflict resolution, and wait for explicit `DESIGN COMPOSITION APPROVED` before implementation.
6. Execute the role contracts in `trickster/roles/` through the active adapter. When separate agents are available, give them constrained inputs and write paths; otherwise use the sequential fallback. Always verify each handoff and independently accept the integrated result. Create `trickster/artifacts/<run-id>/run-state.json`, record every available session ID, and use validated phase handoffs rather than conversation history for cross-phase continuity.
7. Run implementation in three phases under one logical implementation-owner role but separate phase-scoped execution sessions: Core, Full, and Hardening. Core may use fixtures for preview, but should put the primary flow on real local storage early; it also implements the system launch screen, transition to the first real frame, and any contracted app-owned splash, then shows the cold launch in the Core feedback loop. Full starts fresh from the verified Core handoff, completes the remaining scope and all eleven capabilities, and must reach `LOCAL DATA READY`: Release paths use SwiftData, files, or real system APIs, with runtime mocks and preview stores excluded. After Full, create and integrate approved product assets and the applicable approved icon. Hardening starts fresh from the verified Full and visual-integration handoffs, then validates the final local production path, launch experience, UI, failures, persistence, accessibility, compact layout, locales, and asset regressions. At the user's request during any phase, show that revision as a `PREVIEW`, never acceptance evidence.
8. Implement every mandatory capability as contextual behavior with a useful result and denial or unavailable handling. Permission-only buttons and fake devices do not satisfy the contract. CallKit is the sole exception: an honest `INTERFACE_ONLY` experience is allowed when it never claims an established call, signaling, or media transport.
9. After design composition approval, run app-icon research and generation in parallel with implementation. Use the latest image-generation model available in the active environment, record its exact model ID and provenance, show the generated image to the user, and refine the same concept until `APP ICON APPROVED`. Do not integrate it before approval.
10. Record product-asset requirements in the contract, but generate and integrate the assets only after Full reaches `LOCAL DATA READY` and before final Hardening. The accepted build must contain the approved icon and assets.
11. After `APP ACCEPTED`, approve a store-screenshot storyboard, then generate, show, and revise one frame at a time. Do not continue until the current frame has explicit `STORE FRAME <n> APPROVED`; finish with `STORE SET APPROVED`.
12. After app acceptance, store-screenshot approval, and explicit final confirmation, perform cleanup according to `trickster/workflow/finalization.md`.
13. Mark unavailable tools, physical devices, system services, or checks `UNVERIFIED`. The first ten capabilities remain `REAL`; CallKit is verified as `INTERFACE_ONLY`. Mandatory capabilities cannot be `N/A`; do not substitute assumptions for missing evidence.

Do not change criteria, the approved design composition, or references merely to obtain PASS.
