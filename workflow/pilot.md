# Пилот перед массовым использованием

## 1. Подготовка

Выбрать один реальный небольшой продукт или старое задание команды. Описать 3–5 ключевых экранов, основной сценарий и используемый стиль с референсами. Подготовить Xcode, Simulator и инструменты взаимодействия агента. Не запускать новое приложение без задания только ради проверки текста инструкций.

## 2. Проход

Запустить задачу обычным сообщением с мастер-промптом. Разработчик не управляет внутренними этапами. Сохранить продуктовый контракт, делегированные задачи, затраты/время при доступности, сборку и отчёт. Если задание уже выполнялось старым процессом, использовать сопоставимый объём функциональности.

## 3. Оценка

Проверку пилота выполняет владелец процесса; постоянное участие дизайнера не требуется. При наличии старых дизайнерских замечаний использовать их как скрытый набор известных проблем для проверки ревьюера. Наличие таких замечаний не предполагается.

Сравнить часы ручной работы разработчика, число ручных вмешательств, пропущенные дефекты, ложные замечания, новые дефекты после исправлений и итоговое качество по тем же критериям. Отсутствие замечаний агента не считать доказательством качества.

Сначала измерить исходный результат; затем согласовать целевые значения для команды. Не обещать заранее определённый процент экономии.

## 4. Уточнение

Исправить инструкции по реально обнаруженным причинам ошибок. Повторить проверку затронутого сценария; затем проверить подход на другом приложении, желательно в другом стиле. Отделять оценку самого процесса от оценки конкретного стиля.

## Условия перехода к регулярной работе

Агент фактически делегирует задачи; сборка запускается; проверки имеют артефакты; владелец процесса подтвердил приемлемый объём ручной доработки; понятны ограничения и стоимость. Каталог пополняется по мере появления приложений, а не заранее сотнями неподтверждённых описаний.
