# Trickster: iOS app development process

When creating or substantially changing an app:

1. Read `trickster/workflow/master-prompt.md`, `trickster/workflow/orchestration.md`, `trickster/adapters/contract.md`, and the adapter named in `trickster/HARNESS`; execute every applicable stage in order. `ux.md` and `ios.md` apply across all stages.
2. Perform one product-definition stage. Derive the core scope from the request, existing project, and documentation; synthesize all mandatory capabilities; then reconcile the final scope. If that final scope is incomplete or conflicting, ask one question that materially changes the product boundary. Do not add unrequested external infrastructure outside the mandatory capability baseline.
3. Read `trickster/workflow/ios-capabilities.md`. Regardless of the user's prompt, invent and contract one coherent product feature for every capability in this exact order: Bluetooth; Downloading Photos; Adding Photos; Using the Camera; Face ID; Microphone Access; Speech Recognition Access; Contacts Access; Calendar Access; Location Access; CallKit. Preserve their exact IDs, names, and order; do not omit, merge, rename, replace, or mark a row `N/A`.
4. Before UI implementation, load the GitHub catalog, shortlist no more than three suitable apps by metadata, and load documents only for those apps. The user may assign one reference to UI, one to UX, and an optional one to illustrations; the same app may serve more than one concern. Do not mix references per screen or component.
5. Synthesize one coherent local design package in `trickster/design/`, record provenance and conflict resolution, and wait for explicit `DESIGN COMPOSITION APPROVED` before implementation.
6. Execute the role contracts in `trickster/roles/` through the active adapter. When separate agents are available, give them constrained inputs and write paths; otherwise use the sequential fallback. Always verify each handoff and independently accept the integrated result.
7. Run implementation in three phases with the same implementation owner: Core, Full, and Hardening. Core builds the main sections and primary flow, followed by user feedback until `CORE UI APPROVED`; Full completes the remaining scope and all eleven capabilities. After Full, create and integrate approved product assets and the applicable approved icon. Then Hardening validates the final integrated UI across error, denial, unavailable, accessibility, persistence, compact-layout, locale, and asset-regression states. At the user's request during any phase, build, install, and launch that revision in Simulator and show it as a `PREVIEW`, never as acceptance evidence.
8. Implement every mandatory capability as real contextual behavior with a useful result and denial or unavailable handling. Permission-only buttons, fake devices, and fake calls do not satisfy the contract.
9. After design composition approval, run app-icon research and generation in parallel with implementation. Use the latest image-generation model available in the active environment, record its exact model ID and provenance, show the generated image to the user, and refine the same concept until `APP ICON APPROVED`. Do not integrate it before approval.
10. Record product-asset requirements in the contract, but generate and integrate the assets only after Full and before final Hardening. The accepted build must contain the approved icon and assets.
11. After `APP ACCEPTED`, approve a store-screenshot storyboard, then generate, show, and revise one frame at a time. Do not continue until the current frame has explicit `STORE FRAME <n> APPROVED`; finish with `STORE SET APPROVED`.
12. After app acceptance, store-screenshot approval, and explicit final confirmation, perform cleanup according to `trickster/workflow/finalization.md`.
13. Mark unavailable tools, physical devices, real services, or checks `UNVERIFIED`. Mandatory capabilities cannot be `N/A`; do not substitute assumptions for missing evidence.

Do not change criteria, the approved design composition, or references merely to obtain PASS.
