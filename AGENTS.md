# Инструкции проекта

Этот репозиторий содержит npm-installer и переносимый процесс разработки iOS-приложений для разных agent harness. При изменении самого комплекта следуй запросу пользователя; не создавай приложение или исполнителей автоматически ради правок самого процесса.

При задаче на создание или существенное изменение приложения:

1. Прочитай `workflow/master-prompt.md`, `workflow/orchestration.md` и adapter из `HARNESS`; выполняй этапы по порядку. `workflow/ux.md`, `workflow/ios.md` и `workflow/launch-screen.md` действуют сквозным образом.
2. Выполни единый этап product definition: определи core scope по задаче, существующему проекту и документации, затем синтезируй все обязательные capabilities и только после этого зафиксируй final reconciled scope. Каждый Trickster-проект является local-first: durable product data хранится в SwiftData, бинарные данные — файлами, локальная идентичность создаётся автоматически, а `UserDefaults` используется только для небольших настроек. Не добавляй собственный backend, серверные аккаунты, Sign in with Apple, CloudKit или синхронизацию. Если продукт нельзя честно реализовать в этой границе, зафиксируй `CONFLICTING` и задай один вопрос, действительно меняющий scope.
3. Прочитай `workflow/ios-capabilities.md`. Независимо от пользовательского промпта придумай и включи в контракт осмысленную продуктовую функцию для каждой capability строго в этом порядке: Bluetooth; Скачивание фото; Добавление фото; Использование камеры; Face ID; Доступ к микрофону; Доступ к распознаванию речи; Доступ к контактам; Доступ к календарю; Доступ к геолокации; CallKit. Сохрани точные ID, названия и порядок; не пропускай, не объединяй, не переименовывай и не помечай их `N/A`. Только CallKit может быть согласован как `INTERFACE_ONLY` без signaling и media transport; остальные capabilities требуют реального результата.
4. До проектирования UI загрузи `styles/catalog.json` из GitHub, выбери по метаданным до трёх подходящих приложений и загрузи документы только для них. Пользователь может выбрать один reference для `ui`, один для `ux` и необязательный reference для `illustrations`; один и тот же reference может выполнять несколько ролей. Не смешивай приложения по отдельным экранам или компонентам. Синтезируй один согласованный пакет в `trickster/design/` и дождись явного `DESIGN COMPOSITION APPROVED`.
5. Выполняй роль мастера: исполняй role contracts из `roles/` через активный adapter, передавай ограниченные входы и пути записи, проверяй handoff и самостоятельно принимай интегрированный результат. При отсутствии делегирования используй последовательный fallback.
6. Сам создай контракт, план проверок, provenance источников и отчёт. Пользователь не должен переносить сообщения между ролями.
7. Раздели реализацию на Core, Full и Hardening. В Core допустимы fixtures для preview, но primary flow по возможности сразу использует локальное хранилище; реализуй системный launch screen, переход к первому реальному экрану и опциональный app-owned splash из контракта и покажи cold launch в Core feedback loop. После согласования Core реализуй остальной scope и все capabilities; к завершению Full добейся `LOCAL DATA READY`: Release-пути используют SwiftData, файлы или реальные системные API, а runtime-моки и preview stores исключены. Затем создай и внедри утверждённые product assets и применимую app icon и выполни Hardening финального локального контура, включая launch experience. По просьбе пользователя на каждой стадии собери и покажи текущую ревизию как `PREVIEW`, а не acceptance.
8. Реализуй каждую обязательную capability как контекстную функцию с полезным результатом и обработкой отказа или недоступности. Кнопка, которая только вызывает permission prompt, и фальшивые устройства не считаются реализацией. CallKit — единственное исключение: честный `INTERFACE_ONLY` UI допустим, если он не изображает установленное соединение, signaling или media transport.
9. После утверждения design composition параллельно с реализацией запусти app-icon branch. Используй последнюю доступную в среде модель генерации изображений, запиши точный model ID и provenance, покажи изображение пользователю и продолжай ту же концепцию до `APP ICON APPROVED`. До подтверждения не внедряй изображение в Xcode-проект.
10. План product assets входит в контракт, но их генерация и интеграция начинаются только после Full и `LOCAL DATA READY`. Hardening выполняется уже с утверждённой app icon и всеми утверждёнными assets.
11. После независимой приёмки создай store screenshots только из реальных экранов принятой сборки. Сначала согласуй storyboard, затем генерируй и показывай каждый кадр отдельно; не переходи к следующему до `STORE FRAME <n> APPROVED`. После подтверждения всего набора получи финальное подтверждение пользователя и очисти временные загрузки и build artifacts.
12. Если инструменты, физическое устройство, системный сервис или данные недоступны, выполняй независимую работу и явно укажи непроверенные пункты. Первые десять capabilities остаются `REAL` и не могут использовать CallKit-исключение; CallKit проверяется как `INTERFACE_ONLY`. Обязательные capabilities нельзя помечать `N/A`. Не изображай визуальное ревью или успешные тесты.

Явные инструкции пользователя и более приоритетные правила среды сохраняют приоритет. Не меняй критерии, референсы или тестовые ожидания только ради получения PASS.

## Тесты комплекта

Пиши тесты только для исполняемого поведения и устойчивых инвариантов: installer, package contents, schemas, canonical capability data, catalog integrity и сохранность пользовательских artifacts. Не добавляй regex-тесты ради проверки наличия отдельных формулировок в инструкциях; смысловую согласованность prose проверяй ревью документов или структурным валидатором, если появляется реальная машиночитаемая схема.
